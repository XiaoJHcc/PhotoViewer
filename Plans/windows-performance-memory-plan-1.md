# Windows 端性能与内存专项 方案 1

> 范围：Windows 原生壳。主压力：HEIF 连续切换、最近两张对比切换、解码位图内存管理；其次直方图、增强等辅助计算；RAW 主图解码补齐（不设严格指标）；设置页内存提示按新口径重算。
> 红线：任何瞬间不显示低于精度要求的产物（代理长边 = 视口物理长边 × 2，100% 及以上用全分辨率）；只在不可见处省性能。展示编码保持线性 RGBA16F，10 位源不在任何环节降到 8 位。
> 共享层已由 [Apple 专项](apple-performance-memory-plan-1.md) 落地的预取/淘汰/缓冲池/直方图查表/增强复用，Windows 自动继承，本专项不重做。

## 1. 实测基线（i5-13600K 20 线程 / 48 GB / RTX 4080 + UHD 770，2560×1440 @150%）

素材：`D:\照片2026\2026-5-4 湘湖\A7C2`（161 HIF + 161 ARW，a7C II）。HIF 主图为 `grid` 3×2，瓦片 3520×1600 HEVC Rext 4:2:2 10 位，nclx 1/13/5 全范围；另有 1616×1080 与 320×212 HEVC 缩略项、160×120 JPEG。

|---|---|

| RGB24→BGRA / Skia Mitchell → 4532 / → ToScRgb16（全幅） | 30 / 297 / 230 |
| 现网 Full 端到端 / 代理 @4532 端到端 | 2206 / 2272（代理不比 Full 省 CPU） |

| ARW 内嵌 JpgFromRaw 7008×4672 | 66 |

## 2. 决策

1. **HEIF 解码换 FFmpeg HEVC + 瓦片并行**：自建 `pvhevc.dll`（静态链接仅含 hevc 解码器的 LGPL FFmpeg，clang64 + nasm，零外部依赖），托管侧自解析 HEIF 容器（grid/irot/imir/colr/pixi），瓦片按线程并行解码。容器或色彩超出支持面（AV1、PQ/HLG、非恒等 clap 等）回退 libheif。不选 QSV：仅 Intel 核显可用、初始化 435 ms、静默回退难以保证；不选 WIC HEIF：比 FFmpeg 慢 7 倍。
2. **YUV 直出展示编码**：解码产物保持 YUV 平面（10 位不降 8 位），一次融合完成色度上采样 + 矩阵 + 缩放 + 线性化 → RGBA16F，去掉 RGB24→BGRA→Mitchell→skcms 四次整幅搬运。代理缩放用按比例展宽的 Mitchell（抗锯齿，质量不低于现网 Skia Mitchell 直接下采样）；Full 只做逐像素转换。
3. **RAW 走 WIC 系统 RAW 引擎**全分辨率；扩展缺失或失败时，仅当内嵌 JpgFromRaw 与裁切尺寸一致才用它，否则如实停在可得尺寸（与 SCOPE-04 口径一致）。RAW 并发只放 +1。
4. **内存记账改实测**：Windows 专属预算源以进程私有提交（含 D3D 系统内存副本、原生 libheif/FFmpeg 缓冲）为 footprint；接系统低内存通知作 OS 压力源。缓存上限沿用共享推导公式。
5. **主图上传**：保留当前 + 最近 2 张的 GPU 纹理（按展示产物实例命中，不持像素租约），A/B 对比不重传；≥ 32 MB 的纹理由 UI 线程建并映射暂存纹理、后台线程只做行拷贝、UI 线程拷入 mip 链后交换（DirectN 的 COM 包装不能跨线程调用 D3D）；换好之前旧帧留屏。
6. **设置提示**：第一行实测预算；第二行按真实代理字节（F16 × 视口代理面积，封顶照片像素）估算张数。

### 剩余长尾根因

- **W5 的 p95 ≤ 350 ms 未达成**：解码侧已达标（整幅解码 p95 357–427、P0 段 334–381），顺序连翻 p95 本轮仍为 646.9–692.3 ms。慢帧 = 一次 P0 解码（缓存未命中 200–400 ms）+ 一次合成器归还后台缓冲的等待（260–510 ms）；A/B 模式两张都已在缓存、呈现间隔 40 ms，本轮 p95 16.6 ms（100 翻），长尾只出现在冷帧。
- **分段实测**（临时探针，已移除）：每帧恰好一次 `Draw`+`Present`（中位 1、最多 6）；`Present` p50 0.24 ms、p95 15.3（一个垂直同步）、max 16；`UpdateSubresource`+`GenerateMips` ≤ 9 ms。停顿落在 `SetImage` 内"解码完成后第一条碰后台缓冲的命令"上：按调用顺序分别出现在 `OMSetRenderTargets`（19–28 帧/轮）、`QueryVideoMemoryInfo`、清屏或 `Present`；这段时间 UI 线程 CPU 时间为 **0.00 ms**，即被驱动/合成器阻塞，不是被抢占。
- **与本进程 GPU 工作无关**：跳过主图绘制（20 帧停顿）、跳过整幅上传与 mip 链（24 帧）、后台预取并发降到 1（18 帧）都与默认（19–28 帧）同级；停顿幅度与解码时长同量级。
- **停顿来自合成交换链"闲置后"的缓冲归还等待**（空载节拍探针：同一交换链、空画面、不动解码）：连续每 16 ms 呈现 0/40 帧停顿；每 300 ms 呈现 17–19/40 帧停顿、max 435 ms。距上一次呈现超过约 0.3 s 后，下一条碰后台缓冲的命令要等合成器把缓冲还回来，而换图的解码（200–400 ms）正好制造这个间隔。
- **交换链约束**：合成交换链只给应用一张可渲染缓冲——对其余缓冲建 RTV 返回 `E_INVALIDARG`，`GetCurrentBackBufferIndex` 恒为 0（BufferCount 2 与 3 相同）；`SetMaximumFrameLatency` 返回 `DXGI_ERROR_INVALID_CALL`。故"渲染到当前后台缓冲""限制帧延迟抑制积压"两条常规手段在这里都不成立。另试过两种缓解并已回退：换图请求时先补一次呈现、解码等待期间按 30 ms 节拍重复呈现当前帧——顺序连翻 p95 都在 650–700 ms 区间（无改善），后者还带来额外呈现开销。
- **适配器实测**：设备默认落在 Intel UHD 770（适配器 0，本会话唯一接了输出的适配器；RTX 4080 两个 LUID 都没有输出）。用 `EnumAdapterByGpuPreference(HIGH_PERFORMANCE)` 换到 4080 后 `OMSetRenderTargets/清屏` 停顿完全消失（p95 0.01 ms），但 DWM 在 Intel 上合成，每帧多了跨适配器合成代价：p50 33 → 100 ms、p95 613 ms。默认"跟随输出所在适配器"在本机两种情形下都正确，不改。
- **待判定（可能只属本次远程/虚拟显示会话）**：上述 400 ms 级等待在"显示器直连独显"的本地会话里预计不出现——那时设备本来就落在独显上（显存独立、不与 18 路解码争系统内存），实测该配置下停顿为 0。本机是远程会话（OrayIdd/ToDesk/GameViewer 虚拟适配器，1920×1080@96，输出挂在核显），才会稳定复现；需在本地硬件会话按同一脚本复测确认。
- 已排除：解码闸门排队、GC（整轮阻塞暂停合计 284 ms，与慢帧不对应）、LOH 分配、胶片栏缩略图争用、纹理上传 CPU 段、后台解码并发度。
