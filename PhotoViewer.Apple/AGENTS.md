# PhotoViewer.Apple — Apple 平台共享源

`PhotoViewer.Apple/` 是**纯源文件目录**（不是独立 csproj/程序集）：`PhotoViewer.Mac/PhotoViewer.Mac.csproj` 与 `PhotoViewer.iOS/PhotoViewer.iOS.csproj` 都以 `<Compile Include="..\PhotoViewer.Apple\**\*.cs"/>` 链接编译同一目录（I1 起 iPad 原生壳已接入）。

**硬规则**：本目录不得出现 AppKit / UIKit 类型（`NSView`、`NSEvent`、`NSImage`、`NSColor`、`UIView` 等）——iOS 侧无法编译。只允许 Foundation / CoreGraphics / CoreAnimation / ImageIO / Metal 与共享 `PhotoViewer` 项目类型。平台事件字段解包、原生视图与图层挂载、系统图标对象创建一律留在各 head 的 `Native/`、`Core/` 下。

命名空间统一为 `PhotoViewer.Apple`。**几何/视口与命令查询已迁到 [PhotoViewer.Shared](../PhotoViewer.Shared/AGENTS.md)**（`PhotoViewport`、`MainScreenLayout`、`FilmstripGeometry`、`ControlBarLayout`、`AnalysisPanelGeometry`、`SimilarityPanelGeometry`、`ExifTableGeometry`、`InputCommandMap`），本目录只保留 Apple 专属源。改动任一共享源都会同时影响 Mac 与 iOS（Android 也链 `PhotoViewer.Shared`）；合并门 = Mac 八套 `--pv-native-*` 回归零行为变化 + iOS 七套 `--pv-native-*/-check` 回归通过。

| 文件 | 职责 |
|---|---|
| ApplePresentationDecoder.cs | Apple 平台统一主图解码器，按请求编码产出两种表面：RGBA16F 扩展线性 sRGB（代理档，广色域超范围分量不裁剪）或 8 位 Display P3（Full 档/压力降级；RGBA8888 预乘，P3 立方体外的原色钳到 P3 边界）。**RAW 走 Core Image 的 RAW 引擎**（`CIRawFilter`，Mac/iPad 共用）：几何取 `NativeSize`（传感器朝向、未旋转），EXIF 方向先读成产物的方向码再把滤镜 `Orientation` 设为 Up，像素保持未旋转——与 ImageIO 路径「`CreateThumbnailWithTransform=false` + 属性方向」同一契约；代理档 `ScaleFactor = min(1, 目标长边/原生长边)`（Core Image 取整不足时微调缩放，宁大勿小），Full 档为 1，不启用草稿模式；渲染直接写进 `RentPixels` 池化缓冲（F16 用 `CIFormat.Rgbah.GetConstant()` + 扩展线性 sRGB，8 位用 `RGBA8` 原生常量 + Display P3，共用静态 `CIContext`，工作色彩空间为扩展线性 sRGB、不缓存中间结果）。**`CIFormat` 在 .NET 绑定里是普通枚举，枚举值不是原生常量**，直接把 `(int)CIFormat.Rgbah` 传给 `RenderToBitmap` 会被当成别的格式并静默不写像素，必须取 `GetConstant()`。`CIRawFilter` 创建/输出/渲染失败才回退 ImageIO 并打印一行原因（iPad 上该回退即内嵌预览）；JPEG/HEIF 的容器解码恒走 ImageIO：扫描 ICC APP2 后按共享 EXIF 推断无标签色域，无内嵌预览的用户图片按短边缩解码。**Mac 的 HEIC/HEIF/HIF、F16 且产物 ≥4MP** 由 `CIImage.FromCGImage` + 共用 `CIContext` 直接转换进池化缓冲，失败回退 CGBitmapContext，取消不回退；JPEG、小图和 8 位出口保持旧路径。iOS 默认仍用 CGBitmapContext（真机收益未验证），内部布尔构造仅供固定基线对照，不是用户设置。缩略图兜底对 RAW 同样走新路径，出口为显示朝向的 sRGB8。原 `PhotoViewer.Mac/Core/MacPresentationDecoder.cs`。 |
| MetalPhotoRenderer.cs | Metal 渲染核心：设备/队列、MSL 着色器（RGBA16F 顶点变换 + 八方向 UV）、扩展线性 sRGB 的 `CAMetalLayer`（**绘制目标恒为 RGBA16F**，两种主图编码共用）、纹理上传与 blit mipmap、帧编码、导航图等比线性帧读回、纹理字节记账（按实际编码的每像素字节）。纹理格式按展示编码选择：F16 线性 scRGB → `RGBA16Float`；8 位 P3 → `RGBA8Unorm_sRGB`（采样即线性 P3，再由第二条片段管线用 3×3 矩阵 `P3ToExtendedLinearSrgb`（片段 uniform，唯一来源）换算到扩展线性 sRGB）。两种编码共用采样器/UV/方向/mipmap 逻辑，故 F16 代理↔P3 Full 热替换不产生可见色偏。`SetTexture` 先把新纹理分配、上传并生成 mipmap，全部成功后才置换当前纹理；创建或上传失败保留旧纹理、释放半成品。除当前图外，按展示产物弱引用保留最近两份纹理，不持 CPU 租约；非当前合计受 `min(256MiB, 预算/16)` 约束，计入 `TextureBytes`。Caution 起或恢复观察期不保留非当前；探测线程只 `RequestTrim`，宿主派主线程 `ApplyPendingTrim`，不阻塞探测线程。Metal 上传/绘制/读回/释放由同一锁串行。null 显式清屏但允许上一纹理留在最近缓存，绝不自动复活旧图。宿主只负责把 `Layer` 挂到视图并调用 `DrawFrame`；视口数学取共享 `PhotoViewport`。 |
| AppleTextureCacheChecks.cs | 共享 Metal 缓存专项验收：真实上传与 GPU 读回，覆盖 F16 扩展色域/P3/八方向/行距、LRU 与字节上限、空图、失败保留旧帧、并发修剪、弱引用租约与 Dispose。Mac `--pv-native-smoke --pv-native-texture-cache`、iOS `--pv-native-texture-cache-check`；A/B 计时仅 SetTexture 编码，不冒充 GPU 完成或实际呈现。 |
| AppleAcceptanceChecks.cs | Mac `--pv-native-smoke` 与 iOS `--pv-native-photo-check` **共用**的验收判定：GPU EXIF 八方向角点核对（导航图线性帧）、色卡中心像素与期望线性 scRGB 值核对（8 位 P3 产物先经 `ColorEngine` 归一到线性 scRGB）、`ColorExpectation` 按编码给出下界（P3 立方体装不下的 Adobe 红原色按 P3 钳位值）。 |
| AppleInputMapping.cs | 原生事件码 + 修饰键掩码 → 共享 `AppGesture` 的 **Apple 专属解码**：`FromRaw` / `FromHidUsage`、macOS keyCode 与 iOS HID usage → `GestureKey` 表、`AppleKeyboardMapping` 修饰键语义。数值即契约。**键位只认物理位置**：macOS 的字母、主行数字与常用标点按 `NSEvent.KeyCode` 判定（`CharactersIgnoringModifiers` 在非 US 布局下会变成别的字符甚至为空，不参与判定），与 iOS HID usage 表同口径；特殊键与功能键照旧。数字键盘 `+`/`−` 映射到 `OemPlus`/`OemMinus`（与主行 `=`/`−` 同键，才能命中默认预设缩放绑定），数字键盘 Enter 与 Return 都映射到 `Return`。「手势 → 用户命令」的通用查询在共享 `PhotoViewer.Shared/InputCommandMap`，Mac 的 `MacInput.FromEvent/ResolveCommand` 与 iOS `PressesBegan` 共用同一张命令表，派发闸门用 `InputCommandMap.IsCommandKnown`。Android 不得复用本文件，另写 `AndroidInputMapping`。 |
| EnhancementAcceptance.cs | 增强预览的共用验收工具：确定性生成低对比度 JPEG（2400×1600，窄亮度区间渐变 + 平缓色块，只写自有沙盒/输出目录）；两帧 BGRA8 的抽样平均/最大绝对差；**`CreateOrientationJpeg(path, orientation, width, height)`** 生成带 EXIF 方向码的四角异色 JPEG（插入最小 EXIF APP1，不依赖第三方写库）；**`CornerSignatures(image)`** 给导航帧四角分类（红/蓝/绿/白/灰），用于证明增强前后方向与色相排列不变。Mac `--pv-native-analysis` 与 iOS `--pv-native-analysis-check` 都用它证明"增强前后上屏像素明显变化"（平均差 ≥6、最大差 ≥30）与"增强不旋转照片"，只断言 `EnhancedDisplay` 不再足以防止"点了没反应"回归。 |
| ApplePerfProbe.cs | **验收专用性能探针** `--pv-perf-probe <目录>`（Mac/iOS 共用）：目录内前 6 张 HEIC/JPG/ARW 按文件名排序，分段计时属性读取、`CreateThumbnail`（Always/IfAbsent）、全图解码、RGBA16F/8 位 P3 位图绘制、ImageIO 子采样、`CIRAWFilter`（相机列表/全尺寸/超采样 8 位与 F16）、产品解码器的 RAW 全分辨率与代理档（`rawProductFull8`/`rawProductProxy8`，报告源尺寸与方向码）、Metal 上传、直方图、增强三步与分析用 sRGB8；每项跑三次记录首次（冷）与中位数。**RAW 产品路径分解段**（`rawPipe_*`）：`CIRawFilter` 创建、`NativeSize`/`Orientation` 读取、设方向、设 `ScaleFactor`、取 `OutputImage`、`RenderToBitmap` 逐段计时，并对比"每次新建实例（产品口径，冷）"与"复用实例（热）"、设/不设 `Orientation=Up`、`CIContext` 选项（默认 / `CacheIntermediates` / `PriorityRequestLow` / `HighQualityDownsample=false`）、RGBA8 与 RGBAh 输出、`ScaleFactor` 0.25/0.5/0.65/1 的冷口径曲线；`CIRawFilter.Create(NSData)` 未由 .NET 绑定暴露，改用整文件读取耗时说明 I/O 占比。**代理解码并发段**（`decodeConcurrency`）：同一张 HEIC/ARW 按 1/2/3 路并发各解两次，报告每路耗时与总墙钟——HEIC 两路即可把单张 287ms 摊到 250ms、三路 318ms；RAW 两路时其中一路涨到 1400ms、总吞吐不涨（GPU 串行）。目标长边固定 4532（iPad mini 2266×2），报告纯文本；产品路径不调用。`metalSetTexture` 每轮在计时外清除纹理缓存以测真实上传，`metalCachedSetTexture` 单列命中（不含 GPU 完成等待），避免把缓存命中冒充上传加速。另有 **`--pv-perf-raw-compare <目录>`**（Mac 头接线）把 RAW 新路径与 ImageIO 路径逐像素对拍（Full 8 位 P3 / Full F16 / 代理长边、改方向副本的方向码与像素几何、缩略图兜底 sRGB8），源目录只读、改写只作用于自有工作副本，报告 `raw-acceptance.txt`。**`CIContext` 的 RGBAh 位图输出此前被记为"静默不写像素"，实为 `(int)CIFormat.Rgbah` 传的是托管枚举值而非原生常量**；改用 `CIFormat.Rgbah.GetConstant()`（原生 `kCIFormatRGBAh`）后直渲正常，探针与产品路径同口径。 |
| AppleDecodeOptimizationProbe.cs | 验收专用 `--pv-decode-optimize <目录>`：每类 JPEG/HEIF（含 HIF）/ARW 至多两张、代理长边 4532、至少三样本，对照 ImageIO + CGBitmapContext 与 ImageIO + Core Image 转换，以及 RAW 独立开发与同实例代理→Full；报告首次/中位数、像素差、几何方向和原生 footprint，不把已解码表面转换计时当新图解码。Mac 报告在 `artifacts/acceptance/apple-decode-optimization/probe.txt`，iOS 在 `Documents/PhotoViewer/decode-optimization.txt`；素材只读，入口隔离设置/数据库。 |
| AppleHeifThumbnailChecks.cs | 小图取源对照：调用真实平台 HEIF 解码器与强制原图基线，验证 120/400 档尺寸/朝向/色差与不足回退、560 档逐字节相同。Mac `--pv-decode-optimize <目录> --pv-heif-thumbnail-only`；iOS `--pv-heif-thumbnail-check <目录>`，报告 `heif-thumbnail-checks.txt`，输入必须含内嵌 HEVC 缩略项与无内嵌项真实样本。 |
| AppleSymbolNames.cs | 业务命令与主图菜单项 → SF Symbols 名称字符串映射；Mac 与 iOS 主图菜单共用同一组符号名，系统图标对象的创建留在各平台头部。**本表只管 UI**：菜单/按钮仍按图标严格校验（未知命令直接抛出，避免生成无图标控件），但键盘与滚轮的派发闸门是共享 `InputCommandMap.IsCommandKnown`，缺图标不得否决命令执行。 |
| AppleSettingsStore.cs | macOS / iOS 设置文档载体：整个 schemaVersion 2 JSON 存在单个 `NSUserDefaults` 键，`Synchronize()` 返回 false 时抛错；损坏或旧版文档另存带时间戳的唯一备份键，先腾位再写入，最多保留 3 份。解析、版本分类与写回时机归共享 `SettingsRepository`。 |
| AppleViewStateStore.cs | 共享 `IViewStateStore` 的 Apple 实现：每个视图状态一个独立偏好键（`cc.xiaojh.PhotoViewer.ViewState.*`），缺失键返回 null；相似面板展开态等不进入设置文档，也不参与版本与损坏备份。 |
| AppleMemoryFootprint.cs | 内存实测(只做 P/Invoke,不含 AppKit/UIKit):进程侧 `task_info(TASK_VM_INFO)` 的 `phys_footprint`(偏移 144)与 `os_proc_available_memory`;系统侧 `host_statistics64(HOST_VM_INFO64)` 的 `free_count + inactive_count` 页 × `host_page_size` 给出**整机物理可用内存**(`speculative` 页已计入 `free_count`,不重复计数)。P/Invoke 全部显式指针化(mono 解释器对 ref/out 封送有已证实的间歇崩溃风险)。**ABI 依据** xnu `osfmk/mach/vm_statistics.h` 的 `vm_statistics64`(前四个字段为 `natural_t`:free@0/active@4/inactive@8/wire@12)与 `osfmk/mach/host_info.h`(`HOST_VM_INFO64 = 4`,`HOST_VM_INFO64_COUNT = sizeof(vm_statistics64_data_t)/sizeof(integer_t)`,含 rev2 `swapped_count` 时为 40;读取后按返回计数校验后才取字段,老内核字段更少也不越界)。`mach_host_self()` 的 send right 用后 `mach_port_deallocate` 归还,不泄漏端口;`host_page_size` 入口缺失时退回 `Environment.SystemPageSize`。系统可用量读取失败返回 -1(调用方按"未知"呈现,不得回退成进程预算或 `os_proc_available_memory`)。macOS/iOS 预算源共用这一份读法,footprint 含 Metal 纹理与 IOSurface,故"footprint + 可用"即 jetsam 上限。 |
